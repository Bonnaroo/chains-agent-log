# ARCHITECTURE — how Chains actually works, end to end (read this before touching anything)

## The one-sentence version
The app is ONE static HTML file with no server. It runs entirely on the visitor's phone/browser and talks
directly to a Google Firebase database over the internet. GitHub Pages just hosts the file; it does not run code.

## Is a single-HTML app a real way to build a phone app? Yes.
This pattern is called a **Progressive Web App (PWA)**. Real companies ship this way (Starbucks, Twitter/X
Lite, Uber Lite, Pinterest). Tradeoffs vs a "native" App Store app:
- PRO: no app-store review, no Xcode/Android Studio, updates are instant (no user update prompt), works on any
  phone with a browser, one codebase for iOS+Android, free hosting.
- CON: no App Store/Play Store listing by default (you can add a "shortcut" icon to the home screen, which looks
  and feels like a native app once opened, but it isn't distributed through the store). If a real store listing
  is ever wanted, the same HTML can later be wrapped (Capacitor/Cordova) into a real store build with almost no
  rewrite — that is a LATER decision, not a blocker now.
For a friends-league + casual tracker app, this is a sound, common, low-cost way to build it. It is working;
the plan is to refine it, not replace it.

## The 3 layers
1. **Presentation** — index.html (JS/HTML/CSS bundled together), generated by Claude Design (a no-code AI app
   builder), downloaded, and committed to Bonnaroo/chains-app. GitHub Pages serves it at
   https://bonnaroo.github.io/chains-app. This file is a BUILD OUTPUT, not hand-written source — it should only
   ever be regenerated via Design, never hand-edited, because there is no readable "source" to hand-edit from.
2. **Data** — Firebase Realtime Database, project chains-app-f38f8. The app's JS (running on the user's phone)
   reads/writes this directly using a public API key + anonymous sign-in (Google's Firebase Auth issues a device
   identity silently, no password yet). Key nodes today: /playRounds, /liveRounds (Go Throw), /users, /waitlist.
   NOT yet in Firebase (this is the gap): league picks, draft order, standings, the pro event field — these are
   currently BAKED INTO the compiled index.html at build time, which is why changing them requires a full Design
   rebuild instead of just a database write. Migrating these into Firebase (see PHASE 2 below) is the single
   biggest thing that will make this app easier to run and refine.
3. **External data source** — pdga.com (read-only, no login, no official public API for registration status).
   Event field data is currently pulled manually/by an agent and baked into a build; once migrated to Firebase
   (layer 2) this becomes a simple data push instead of a rebuild.

## Deploy pipeline (now automated, as of 2026-07-28)
Design finishes a build -> agent downloads the exported index.html -> agent PUTs it straight to Bonnaroo/chains-app
via the GitHub API (see kb/github.md) -> live instantly. No more manual step from the owner, no more browser
upload for the GitHub side. Design itself still requires a browser (it has no API), but GitHub no longer does.

## PHASE 2 — the migration that fixes "everything requires a full rebuild"
GOAL: move league/picks/draft-order/standings/event-field data out of the compiled HTML and into Firebase, the
same way rounds and waitlist signups already work. Once done: opening picks, fixing a pick, updating the field,
posting scores = a database write an agent can do via API in seconds, NOT a Design rebuild + redeploy. The app's
JS still needs ONE Design build to change it from reading baked-in data to reading these Firebase nodes at
runtime — after that one build, all FUTURE data changes are backend-only.
STATUS: not yet started. This is the top CEO/PM priority right after the picks-permission fix (see FROM_OWNER.md).

## The 6 principles every build must satisfy (from ROADMAP.md, do not relax these)
Way out on every screen (back/cancel/close always reachable) - destructive/in-progress actions (delete round,
leave league, cancel a live round) reachable with confirm - data survives refresh - adversarial-by-default
(assume users are careless AND clever) - truth of data (real player field, real league members, cross-checked)
- security/least privilege (real auth eventually, own-data-only, sane Firebase rules).
