## A. Firebase rules v2: six shared nodes

Firebase Realtime Database `.write` permissions cascade to every child. A rule at a record level therefore permits changing or deleting any field beneath that record. `.validate` can constrain surviving data, but does not run for deletions.

| Node | What v2 currently permits | What a bad write can do | Narrowest workable direction |
|---|---|---|---|
| `courseStats/{course}/{roundId}` | **Any signed-in user** can create, replace, edit, or delete any round's course-board record, including `players`, scores, date, pars, and `ownerKey`. | Falsify records, rankings, titles, challenges, and call-out results; erase another card's result. | Permit only a participant in the matching **final** `sharedRounds/{roundId}` to create/update that course and round ID. Keep course/round identity immutable and validate shape and score ranges. Cardmates must retain the ability to publish when the owner's phone is closed. This is containment, not proof of honest scores: the shared round itself must also be secured. |
| `territory/{course}` | **Any signed-in user** can replace/delete the whole course object or any `holes`, `held`, `crowns`, `heldLog`, or `meta` child. | Give themselves titles, remove another holder, falsify title history, or wipe a course's territory. | There is **no trustworthy client-only rule with the current write shape**: `ChainsTakeover.sync` writes derived winners without a source round ID at these paths. Move calculation/writes to trusted backend code, with client writes denied. As an interim measure, validate structure and prevent whole-course replacement/deletion, but do not treat that as secure title enforcement. |
| `callouts/{id}` | **Any signed-in user** can create, edit, settle, change winner, or delete anyone's call-out. | Forge challenges between people, falsely award a win, or erase a result. | On create, require `from` to equal the caller's stable identity, `to` to be a valid different user, `status = open`, and immutable parties/week/creation time. For later writes, restrict to the two participants and only the permitted state transition. Because any client currently calls `settle()` and supplies `winner`, a trustworthy winner requires backend calculation from protected final scores. |
| `courseFirsts/{course}/{id}` | **Any signed-in user** can fill any empty first; `!data.exists()` prevents later edits but still permits deletion when the record did not previously exist, and a dishonest first can become permanent. | Claim a first with a fabricated player, date, or round before the real result is recorded. | Allow append only for a participant in the cited final `roundId`; require a known first ID, `key` present in that round, matching course, and immutable non-null record. This still cannot prove "earliest qualifying round" from client assertions. Trusted backend derivation is needed for authoritative firsts. |
| `weekly/{week}/{key}` | Only a signed-in user whose profile identity matches `{key}` can write that **entire card**. They can set any `name`, `done`, `total`, `bonus`, `rounds`, `best`, or `bestCourse`, or delete their own card. | Inflate their own public weekly standing or impersonate a display name. They cannot directly edit another key under the current identity check. | Keep the self-key restriction; require the week format/current accepted window, fixed fields, expected types and bounds, and a name tied to the profile. For standings that must be trusted, derive `done`, `rounds`, and `best` from final rounds on a backend. The current client computes and publishes these values. |
| `usernames/{username}` | On creation, `uid` must be the caller's UID. Once it exists, the matching UID can rewrite **any field**, including `uid`, `name`, `photo`, `points`, and `badge`, or delete the entry. | Hijack or abandon a username mapping, spoof public identity, inflate trophy points, or attach a misleading badge. | Bind `{username}` to the caller's canonical profile name; require `uid` to remain exactly the caller's UID on every surviving write and prevent reassignment. Validate allowed fields, types, and photo size. Self-edited name/photo can remain client writable; authoritative `points` and earned badge eligibility require server derivation. Check the existing whole-record `.set()` in module 070 when designing field restrictions so a normal sign-in does not erase valid optional fields. |

**Publication gate:** The rules file should not be presented as protection against score/title tampering yet. The app's client computes and writes several contested outcomes, and `sharedRounds/{id}` itself currently allows any signed-in user to create a record. Restricting only the six nodes would leave a route to forged source data. Test the revised rules with two identities and the actual cardmate finish path before Guillermo publishes them. This is an inference from the rules and source write paths, not a test of the deployed rules.

## B. Isolated restore drill for one node

The backup kit (`ops/backups-kit/README.md`) describes `full-YYYY-MM-DD.json` with top-level node keys and `_meta.nodes` counts. Its script attempts 33 app nodes plus legacy nodes; bot authentication is needed for private reads. Confirm the chosen backup reports the node as a **number**, not an `ERROR` string, and that the workflow completed successfully. A dated file's existence alone is insufficient.

1. Choose one recent backup from the **private** backup repo. Record its commit, `taken_at`, and `_meta.nodes.courseStats`. Do not paste its contents into chat or a public repo.
2. Use a **separate Firebase test project and Realtime Database**. Write down its project ID and database URL. Confirm they differ from production `chains-app-f38f8`.
3. Locally extract only the top-level `courseStats` value into `courseStats-restore-test.json`. Do not import `_meta`, `_legacy`, or the full root. Compute a SHA-256 hash of a canonical JSON representation (sorted keys, compact separators) and count the top-level course keys and total round records.
4. In the **test project's** Firebase console, select/create its `courseStats` node and use **Import JSON** with that extracted file. Firebase's console import operates on the selected node.
5. Export that same `courseStats` node from the test project. Canonicalize its JSON the same way and compare SHA-256 hashes. Also compare course count, round count, and a few nested player/hole-score records. A matching count alone is not a pass.
6. Record the backup commit and timestamp, isolated project ID, source and exported hashes, counts, result, and any import errors. **Pass** requires exact canonical JSON equality and no production write. If it fails, retain the test project and investigate the mismatch; do not attempt a production restore.

The code for the built app is recoverable from Git history separately. This drill establishes whether a particular **Firebase node backup** can be restored accurately. It does not establish that every node is covered or that cross-node relationships survive a full recovery.
